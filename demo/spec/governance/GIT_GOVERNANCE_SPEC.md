# Git 协作治理 SPEC（governance）

- **状态**：governance（持续生效）
- **更新于**：2026-06-10

## 1. 分支纪律（不可妥协）

**禁止在主分支（`main` / `master`）上直接修改代码或 spec。**

所有改动必须在任务分支上进行，分支命名格式：

```text
<prefix>/<任务名>
```

### 允许的前缀

| 前缀 | 用途 |
|---|---|
| `feature/` | 新功能、新页面、新能力 |
| `bugfix/` | 缺陷修复 |
| `update/` | 配置、依赖、非功能性维护 |
| `refactor/` | 行为不变的结构调整 |
| `docs/` | 仅文档 / spec 文案调整 |

### 命名示例

- `feature/navigation-pages`
- `bugfix/cta-link-broken`
- `docs/git-governance-spec`

### 工作流

1. 从 `main` 拉取最新代码。
2. 创建任务分支：`<prefix>/<任务名>`。
3. 在任务分支上修改代码与 spec。
4. 用户明确允许提交后，再 `git add` / `git commit`。
5. 合并回 `main` 前须经 review（人工或 PR）。

## 2. 提交纪律（不可妥协）

**未经用户明确说「可以提交」，不得执行 `git commit`、`git push` 或等价的版本提交操作。**

- 可以在工作区修改文件、创建分支、暂存改动（`git add`）前的准备。
- 用户说「可以提交」「提交吧」「commit」等明确指令后，方可提交。
- 提交信息应简洁说明「为什么改」，遵循 `type(scope): 描述` 风格。

## 3. 验收

- [ ] 当前工作分支不是 `main` / `master`（除非用户明确要求直接在主分支操作）
- [ ] 分支名符合 `<prefix>/<任务名>` 格式
- [ ] 提交动作仅在用户授权后执行
